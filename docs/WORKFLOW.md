# 给 AI 宿主的阅读工作流

启用阅读之间时，继续自然讨论，不主动把阅读变成测验，不要求用户填写标签或逐条确认保存。

1. 判断新增内容是否值得保留：新的个人洞察、开放问题、确有用途的新知、明确认可的方法，或旧观点的修正。跳过普通寒暄、即时选书与阅读时长问答。
2. 先调用 `find_related`，必要时换同义词；它只返回关键词候选，语义关联由你判断。调用 `get_knowledge_map` 取得当前修订号和已有 ID。
3. 为同一概念复用节点。为不同例子、挑战或修正建立新节点，连接旧思考；不为相似关键词强行连线。
4. 准确区分 `user` / `ai` / `external`。用户的探索问句保持 `open`；尚未认可的 AI 解释保持 `proposed`；只有明确采纳才用 `accepted`；外部核验确有证据才用 `verified`。
5. 原话和整理分开；`quote_attribution` 表明原话作者，尤其区分“AI 提出方法”和“用户表示认可”。来源 URL 和消息 ID 仅在确实可获得时填写，不编造聊天链接。
6. 每条关系使用明确类型和具体理由。一个批次调用 `capture_reading_batch`，使用当前 `expected_revision` 和唯一 `request_id`。
7. 不确定写入结果时，用相同 ID 和相同内容重试。遇到版本冲突先重新读取，再判断如何合并，避免覆盖别人刚做的编辑。
8. 只有工具确认后才能说已保存。平时安静记录，用户想回看时再打开地图。遵守宿主客户端本身的权限机制。

不能假设自动获得全部聊天历史、退出后持续监听、定时同步或每轮必然触发。插件后端没有自己的大模型；提炼和关联依赖宿主执行上述流程。
